## Architecture assessment

The main dependency direction is now:

```text
ForgeConductorApp / ForgeConductorCLI
                 -> ForgeConductorCore protocols and services
                    -> Apple-native infrastructure
```

LM Studio side effects are behind `LMStudioPluginInstalling` and `MCPServeVerifying`. Tool features are modular `ToolPackHandling` implementations. Domain connector roles and health do not depend on LM Studio filesystem details or the GUI.

The persistent `ManagerNode` is the sole dashboard listener. When the GUI sees the manager PID or Forge-owned port, it composes a `ManagerDashboardClient` and controls the manager through its typed loopback API. This prevents duplicate ownership while preserving Start/Stop/Restart/Settings behavior and reconnect polling.

This satisfies the requested object-oriented and modular framework direction. Further splitting Core into separate Swift packages is possible, but is not required to maintain the current boundaries.

## Fail-forward contract

1. Smoke the selected binary independently as primary and fallback.
2. Refuse mutation on role mismatch or malformed existing configuration.
3. Stage and validate both plugin representations.
4. Commit fallback before primary, then atomically replace `mcp.json`.
5. Re-smoke both roles after commit.
6. Roll back on commit/validation failure.
7. Report `ready`, `primary_only`, `fallback_promoted`, or `unavailable`.

This provides two hot, independently launchable MCP connectors. LM Studio is still the host: both registrations must be enabled there, and its routing/operator policy chooses which server handles a call.

## Residual risks / release gates

1. **Apple distribution signing:** the project-local development bundle is ad-hoc signed. A valid Apple Development/Developer ID identity and notarization workflow are still required for distribution.
2. **Local Xcode Build Service:** on this machine, `xcodebuild` currently deadlocks in Swift Build Service while draining a Clang `-E -dM` capability probe, before compiling project source. SwiftPM compiles and links the same native sources successfully. This is a local Xcode service/toolchain issue, not a Forge compiler diagnostic.
3. **LM Studio failover acceptance:** deployment now owns configuration editing, hot reload/relaunch, and host-originated readiness verification. A deliberate primary-termination exercise is still recommended before release to validate LM Studio's operator/routing behavior under loss.
4. **Powerful shell capability:** `shell_exec` is restricted to active agent workspaces and no longer browser-accessible, but it is intentionally not an OS sandbox. Grant it only to trusted local agents.
5. **LM Studio installation integrity:** `/Applications/LM Studio.app` currently reports an invalid modified code signature under `codesign --verify --deep --strict`. Launch Services still relaunched LM Studio and the final deployment synchronized successfully, but reinstalling the official LM Studio build is recommended before release so host integrity cannot become a future availability failure.

## Release recommendation

Proceed to an operator acceptance build after resolving signing and the local Xcode service. Release only after LM Studio shows both role-correct connectors and a primary-loss exercise confirms continued tool access through fallback.
