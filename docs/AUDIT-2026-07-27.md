# Forge Conductor investigation and remediation audit — 2026-07-27

## Scope

This audit covers the seven reported native-app presentation/telemetry issues, the
LM Studio MCP registrations, Forge Conductor audit and manager logs, macOS crash
reports, process execution reliability, manager artifact installation, and release
verification.

The investigation was read-only against the installed manager and LM Studio
configuration. It did not reinstall, restart, replace, or delete the installed
manager, LM Studio registrations, historical logs, or crash reports.

## Reported issues and disposition

| 1 | `ORCH` is red | The aggregate presentation could promote configuration, idle, policy-denial, or warning evidence to an operational failure color. | Added a typed status-tone model and an orchestration policy that distinguishes healthy, informational, caution, failure, and unavailable evidence. ## Crash investigation

### ProcessRunner crash

The July 24 crash report records an uncaught `NSInvalidArgumentException` caused
by reading `NSConcreteTask.terminationStatus` while the task was still running.
The backtrace enters `ProcessRunner`, `ProcessMetricsCollector`, and the telemetry
refresh queue.

The runner now:

- reads `terminationStatus` only after confirmed `waitUntilExit()` completion;
- applies TERM, then KILL, then returns a typed error if termination is still
  unconfirmed;
- stops synchronized output handlers before a bounded nonblocking drain;
- does not wait for EOF from descendants that inherited stdout/stderr;
- preserves surrounding diagnostics when subprocess bytes contain malformed UTF-8;
- caps captured output without splitting into an invalid conversion path.

One residual limitation remains: signals target the direct child PID. A descendant
that deliberately survives reader closure can outlive the call. Full tree
termination would require an isolated process group.

### July 27 AppKit reports

Three July 27 reports were created by the diagnostic launch harness while directly
starting GUI executables outside the normal LaunchServices path. All abort in
AppKit's application registration (`_RegisterApplication`) before Forge application
logic runs. Their process ancestry ties them to that controlled launch attempt.
They are not evidence of the July 24 ProcessRunner defect or an MCP protocol
failure. Final canonical LaunchServices execution succeeded: the distribution
process remained live, and macOS accessibility reported one frontmost window named
`Forge Conductor`. Static screen capture remained unavailable at the operating
system permission layer.

### Repeated-launch window recovery

UI automation exposed a separate lifecycle defect after the first successful run:
the exact foreground app process completed bootstrap but owned zero windows.
Accessibility hierarchy and the Xcode screen recording independently confirmed a
menu-only process rather than a stale element query or a crash.

The main window now has one authoritative owner: a retained AppKit
`NSWindowController` that hosts the SwiftUI `ContentView` with the delegate's single
`AppModel`. It creates the window once per process, reuses it after close, disables
window tabbing, and handles Dock reopen without allowing AppKit to perform a second
default reopen. The only SwiftUI-owned scene is the secondary Settings window.
This design cannot create a second application model, manager, telemetry engine,
or persistent store, and the UI regression test now asserts exactly one main
window after launch.

## Manager installation hardening

Manager artifact installation now stages the executable, frameworks, app bundle,
and command link as same-directory siblings, validates all staged artifacts, and
commits them as one rollback-capable transaction. Copy, signing, verification, and
replacement failures preserve the prior installation.

Code-signing policy is verify-first and fail-closed:

- a valid signature is preserved without replacement;
- an invalid CMS/team signature is rejected;
- ambiguous signature metadata is rejected;
- only unsigned or invalid ad-hoc development artifacts are eligible for fallback
  signing;
- fallback signing uses a stable identifier and hardened-runtime flags;
- signing never uses recursive `--deep`, which would overwrite nested identities;
- app and framework verification remains strict and nested.
